## Extraction Patterns — Real Shapes to Recognize and Adapt

These are distilled from the identity content that used to live only in static, persona-specific system-prompt documents — not copied verbatim, reduced to the underlying shape so you can recognize "this sounds like that pattern" and adapt it, rather than needing a new bespoke document for every kind of user. Treat these as starting points for a draft, never as a rigid template to force a fit.

**Personal, organically-growing (the "Heather" pattern):** starts minimal — a handful of universal, low-commitment categories rather than a fully worked-out structure. Grows its own shape only when a real recurring pattern shows up (roughly three or more related entries that don't fit anywhere existing) — propose a new package by name and explain the pattern, let the user confirm before creating it. Watch equally for the opposite problem: one category quietly becoming a junk drawer for several unrelated recurring themes.

**Multi-venture entrepreneur:** captures market observations, customer conversations, strategic decisions, and lessons across several projects/ventures running in parallel — the core value is nothing falling through the cracks during context-switching, plus pattern recognition *across* the different ventures, not just within one.

**Marketing:** what messaging lands and what doesn't, which channels/campaigns actually move a specific audience, the brand-voice decisions behind the copy, launch/PR moments worth remembering later. Often pairs a personal working repo with read-only access to a shared organizational repo for broader context.

**Product manager:** capture across marketing, sales, product development, trade shows, and operations — the job is inherently cross-functional context-switching, so the value is a single place nothing gets lost, not a narrow single-department log.

**Graduate research:** track what's learned, the decisions that shape research direction, building a structured, searchable base that grows from coursework through dissertation — long time horizon, cumulative, direction-setting decisions matter as much as findings.

**Real estate / multi-hat operator:** captures across genuinely different roles the same person holds (agent, property manager, business owner) — market comps and showing feedback, tenant/maintenance/owner reporting, client advice and the reasoning behind it, even product decisions for tools the person's team is building. The signature is one person wearing several distinct hats, not one role viewed from several angles.

**Systems engineer with a connected Capella model:** the knowledge repo pairs with direct read/write access to an actual engineering model (via `capella-fabric`) — observations/decisions/lessons about the *engineering work itself*, distinct from the model's own content. Watch for the same cross-server confusion this manual's `getting_started` package already covers: logging is `knowledge_repo`'s job, the model is `capella-fabric`'s.

**If none of these fit well:** that's fine — draft something new from what the user actually describes rather than forcing one of these shapes. These patterns exist to speed up recognition of a common case, not to constrain what's possible.

**Reference:** the original persona documents these patterns were distilled from (`docs/Cartenza_Heather_System_Prompt_v1.md`, `Cartenza_System_Prompt_Entrepreneur_v1.md`, `Cartenza_Marketing_System_Prompt_v1.md`, `Cartenza_System_Prompt_Product_Manager_v2.md`, `Cartenza_System_Prompt_Graduate_Research_v1.md`, `Cartenza_System_Prompt_RealEstate_v1.md`, `Cartenza_SE_with_Capella_MCP_System_Prompt_v1.md`, in `se-knowledge-partner`) — still live and in use; this package doesn't replace them, it generalizes their content for agents establishing purpose/behavior_config live, in-repo.
