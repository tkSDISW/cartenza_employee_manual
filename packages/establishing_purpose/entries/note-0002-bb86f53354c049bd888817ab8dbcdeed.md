## The Trigger — and How to Run the Extraction

**The trigger: `get_repo_config`'s own `not_found` result.** After cloning a repo, check `get_repo_config(config_type="purpose")` and `get_repo_config(config_type="behavior_config")` (you should already be doing this before writing any content entry, per `knowledge-repo`'s own instructions). If either comes back `{"status": "not_found", ...}`, that's the signal to *offer* establishing it — no separate polling mechanism needed, this check already exists for another reason and doubles as the trigger.

**This is an offer, not a gate, and the precedence is explicit:**

1. **Check once** per repo per session — not before every write.
2. **A missing `purpose` or `behavior_config` never blocks requested work.** Do what was asked; fall back to general judgment for shape and calibration.
3. **Offer establishment once**, briefly, when it is naturally relevant — typically right after a first real piece of work in a fresh repo. If the user doesn't engage, don't raise it again that session.

Reading "check this before writing content" as a precondition is the failure mode worth avoiding: it turns a helpful offer into a gate in front of the work someone actually asked for.

**Reference repos are exempt.** A curated, published repo — this handbook among them — is not a workspace awaiting configuration, and an agent that offers to establish a purpose for it has misread what it is.

## How to Run It: Draft First, Then Confirm

**Don't open with a cold interview.** Look at what's already there before asking anything:
- The repo's name and any existing packages/entries — even a little existing content tells you a lot about what it's actually for.
- What the user just asked you to do, or anything said earlier in the conversation about who they are or what they're trying to accomplish.

**Draft a reasonable `purpose` and `behavior_config` from that context, then show the draft and ask for confirmation or edits.** This is much lower-friction than an interrogation, and most of the time enough context already exists to draft something genuinely useful — the user is confirming/refining, not building from a blank page.

**Only fall back to a couple of short clarifying questions** if there's genuinely not enough context to draft anything reasonable — e.g. a freshly created, completely empty repo with no conversation history yet to draw from. Even then, keep it to the essentials: what's this repo for, and roughly how do you want entries to read (terse and dense, or more narrative)?

**Once confirmed, write both:**
```
add_log_entry(package=<any>, entry_type="purpose", text=<the purpose text>)
add_log_entry(package=<any>, entry_type="behavior_config", text=<the calibration text>)
```

Either may live in any package — `get_repo_config` finds them repo-wide regardless of where they land.

## One Entry Each — but Purpose Is Meant to Grow

**Both are discovered as singletons, and that has teeth.** `get_repo_config` scans every package for entries of the type. If it finds more than one, it does not pick a winner — it returns **`status: "conflict"`**, lists the matches, and asks a human to resolve it. Until someone does, every caller asking for that config gets nothing.

So the rule is the same for both: **one entry, found in place, never a second one.**

**But `purpose` and `behavior_config` change differently over time, and it's worth knowing which you're doing.**

**`behavior_config` gets revised.** Calibration replaces calibration — when rigor expectations change, the old statement is simply no longer what you want. Revise in place:

```
add_log_entry(entry_id=<the one you found>, entry_type="behavior_config", text=<the new calibration>)
```

**`purpose` accumulates.** A repo's purpose genuinely develops — it gets refined, extended, given new context as the work grows — and that history is worth keeping visible rather than overwriting. Add to the existing entry instead:

```
append_log_entry(package=<its package>, entry_id=<the one you found>, text=<what's new>)
```

That appends a dated section under a horizontal rule, leaving everything before it intact. The purpose entry becomes a record of how the repo's intent developed, not just a snapshot of where it landed — while remaining the single entry `get_repo_config` can still answer with.

**Why not simply add a second purpose entry?** Because that is precisely what produces the `conflict` result above, and it breaks purpose discovery for everyone using the repo. Accumulation belongs *inside* the entry.
