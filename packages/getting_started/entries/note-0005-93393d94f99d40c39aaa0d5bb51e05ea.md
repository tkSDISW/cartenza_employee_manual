## Every Repo Has a Purpose and a Calibration — Find Them Before You Write

Two entries answer "what is this repo for" and "how should things be written here." They are worth finding early, because they change how you work in a repo — and because they are easy to miss: they live as ordinary entries inside whatever package they happened to be logged in.

| | What it answers | How it changes over time |
|---|---|---|
| **`purpose`** | What this repo is for, and who it serves | **Accumulates** — appended to as the repo's intent develops |
| **`behavior_config`** | How much rigor, what "good" looks like here | **Revised** — replaced in place when expectations change |

**Finding them takes one call each, not a search:**

```
get_repo_config(config_type="purpose")
get_repo_config(config_type="behavior_config")
```

That scans every package and returns the match wherever it lives. Don't guess a package and don't browse them one by one — there is no "config lives in the first package" rule.

**Three results, and each means something different:**

- **`ok`** — apply what it says.
- **`not_found`** — this repo hasn't established one. Don't stop: fall back to general judgment and carry on with what was asked. It's worth *offering* to establish one at a natural moment, once. The `establishing_purpose` package covers how.
- **`conflict`** — someone created a second entry of that type. Discovery now refuses to answer for everyone until a human merges or removes one. If you see this, say so; don't pick one yourself.

**The one rule that prevents `conflict`: never add a second `purpose` or `behavior_config`.** Search first, then either append to or revise the one that exists.

That rule can look like it forbids a repo's purpose from developing. It doesn't. **Purpose is meant to grow** — a repo's intent gets refined and extended as real work happens, and that history is worth keeping. The growth goes *inside* the single entry, via `append_log_entry`, which adds a dated section and leaves everything before it intact. What you end up with is a record of how the repo's purpose developed, still answerable by a single lookup.

`behavior_config` is different in kind: new calibration supersedes old calibration rather than adding to it, so that one is revised in place with `add_log_entry(entry_id=...)`.

**Reference:** `knowledge_packages` package (the full treatment of config entries, including `{type}_configuration` and repo-wide discovery), `establishing_purpose` package (how to establish these for a repo that has neither).
