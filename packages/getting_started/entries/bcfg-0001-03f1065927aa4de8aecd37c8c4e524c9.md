## What This Repo Is, and What Not to Confuse It With

This repo is **curated onboarding content** — a groomed, role/behavior-focused handbook for anyone (human or agent) stepping into Cartenza work. It is deliberately **not**:

- **Cartenza's internal design log** — every addendum and course-correction, valuable for understanding *why* the architecture is shaped as it is, but not written to orient someone new. This handbook pulls curated, generalized content *from* that material; it doesn't replace it or duplicate its addendum-by-addendum style.
- **The MCP servers' own build log** — Cousin's working record for the servers themselves. This handbook started from that log's `behavior_config` as a style template, but is its own separate, generalized artifact — not a mirror or a sync target.
- **The assignment record** — Tony's log of work requested *of* Cousin, viewed from his side. Related to this handbook's origin story, but not the same content.

**If ever unsure whether something belongs here:** ask "would this genuinely help someone new understand how to work in Cartenza, in a durable, generalized way" — if yes, curate it in; if it's blow-by-blow design reasoning specific to one moment in one thread, it belongs in an internal design-log repo instead, referenced from here rather than duplicated.

---

## Logging Discipline for This Repo Specifically

1. **Curated, not addendum-heavy.** Unlike an internal design log, entries here should read as settled, generalized guidance — not a live design thread with many "not yet resolved" open questions. If something is still genuinely unsettled, say so plainly and briefly, but don't let the entry become the design conversation itself.
2. **Write for someone with zero prior context.** Every entry should make sense to a reader who has never seen any other Cartenza repo — link out for depth, don't assume it.
3. **Prefer the shape already established**: constraint → response → what it looks like in practice → a concrete signal for "you're at this level" → reference. Not mandatory for every entry, but a good default for staircase-level content specifically.
4. **Status field discipline**: revise in place via `entry_id` (or `append_log_entry` for genuine addenda) — never delete, never silently rewrite history.

## Access Model

**Live scope discovery is authoritative — this page is not.** Call `list_my_scopes(agent_id=...)` or `list_my_scopes(api_key=...)` to find out what you can actually read and write here. Which named agents hold write access is operational state that changes without this entry being edited, so any list of names written here would go stale silently and be believed anyway.

This is the plain, inspectable git-repo stage of the handbook, not the eventual server-side form — that migration is a deliberate future step, not a gap to work around now.
