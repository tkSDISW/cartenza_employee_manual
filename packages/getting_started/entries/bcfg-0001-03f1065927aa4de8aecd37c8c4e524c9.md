## What This Repo Is, and What Not to Confuse It With

This repo is **curated onboarding content** — a groomed, role/behavior-focused manual for anyone (human or agent) stepping into Cartenza work. It is deliberately **not**:

- **`cartenza_capabilities`** (in `tkSDISW/knowledge_partner`) — that's the raw design log: every addendum, every course-correction, valuable for understanding *why* the architecture is shaped as it is, but not written to orient someone new. This manual pulls curated, generalized content *from* threads like that one — it doesn't replace it or duplicate its addendum-by-addendum style.
- **`cousin_repo`/`cartenza_mcp`** (in `tkomarOSP/claude_code`) — Cousin's own build log for the MCP servers he works on. This manual started from that repo's `bcfg-0001` as a style template, but is its own, separate, generalized artifact — not a mirror or a sync target.
- **`cousin_back_log`** (in `tkSDISW/knowledge_partner`) — Tony's record of assignments *to* Cousin, viewed from Tony's side. Related to this manual's own origin story, but not the same content.

**If ever unsure whether something belongs here:** ask "would this genuinely help someone new understand how to work in Cartenza, in a durable, generalized way" — if yes, curate it in; if it's blow-by-blow design reasoning specific to one moment in one thread, it belongs in a `cousin_back_log`/`cartenza_capabilities`-style repo instead, referenced from here rather than duplicated.

---

## Logging Discipline for This Repo Specifically

1. **Curated, not addendum-heavy.** Unlike `cousin_back_log`/`cartenza_capabilities`, entries here should read as settled, generalized guidance — not a live design thread with many "not yet resolved" open questions. If something is still genuinely unsettled, say so plainly and briefly, but don't let the entry become the design conversation itself.
2. **Write for someone with zero prior context.** Every entry should make sense to a reader who has never seen any other Cartenza repo — link out for depth, don't assume it.
3. **Prefer the shape already established**: constraint → response → what it looks like in practice → a concrete signal for "you're at this level" → reference. Not mandatory for every entry, but a good default for staircase-level content specifically.
4. **Status field discipline, same as `bcfg-0001`**: revise in place via `entry_id` (or `append_log_entry` for genuine addenda) — never delete, never silently rewrite history.
