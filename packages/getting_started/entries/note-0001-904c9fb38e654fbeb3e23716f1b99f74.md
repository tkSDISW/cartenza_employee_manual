## Which MCP Server Do I Use?

**If you take away one thing from this manual before doing anything else, take this.** Cartenza is several separate MCP servers, not one — and their names/vocabulary overlap enough (all deal in "packages," "artifacts," read/write operations) that picking the wrong one is an easy, real mistake. This exact confusion happened: a ChatGPT session once reached for `project_artifact_repo`'s tools to log a note, when the right server was `knowledge_repo` — and had to be manually corrected by a human before it could proceed (`cousin_back_log`/note-0050).

**Check this table before guessing.** Each server's own `instructions` field (visible when you connect to it) also states this — but if you have several connected at once, it's easy to reach for the wrong one out of habit rather than actually checking.

| I want to... | Use this server | Not this one |
|---|---|---|
| Log a note, observation, decision, or lesson learned — or append to one | **`knowledge_repo`** (`add_log_entry`/`append_log_entry`) | `workspace_manager`, `project_artifact_repo` |
| Produce a typed working output (table, yaml, text, html, json, etc.) as part of running a routine | **`workspace_manager`** | `knowledge_repo` |
| Promote a finished output (FMEA, Pugh matrix, trade study, requirements impact analysis) into its permanent home | **`project_artifact_repo`** | `workspace_manager` (it only holds the working version) |
| Read, browse, query, or modify an actual Capella system model (OA/SA/LA/PA, requirements, diagrams) | **`capella-fabric`** | any of the above three — none of them touch Capella models at all |

**The underlying shape, if you want the "why" behind the table:** Cartenza's knowledge work happens in layers. `knowledge_repo` is the durable log — the Log Book layer, the foundation everything else sits on. `workspace_manager` is scratch space for a routine's working outputs. `project_artifact_repo` is where a *finished, promoted* output actually lives long-term — distinct from the workspace it was drafted in. `capella-fabric` is a different axis entirely: it's not about logging knowledge at all, it's direct access to an engineering model. See the `log_book` package in this manual for more on why the Log Book layer exists and what it solves.

**If you're ever unsure which server owns a task and none of the above resolves it:** say so explicitly rather than guessing — a wrong tool call on the wrong server is exactly the kind of mistake this page exists to prevent.

**Reference:** `cousin_back_log`/note-0050 (the design history and the real incident that motivated this page), each server's own `instructions` field (the compressed, in-tool-list version of this same guidance).
