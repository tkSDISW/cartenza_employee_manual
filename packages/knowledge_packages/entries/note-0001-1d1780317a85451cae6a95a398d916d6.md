## Level 2 — Knowledge Packages: Make What You Captured Findable Again

**The constraint this solves:** "I already solved this." A chronological log prevents loss, but a growing log creates a new problem — finding and reusing the important pieces once there are hundreds of entries instead of a handful. A pile of notes isn't yet reusable knowledge.

**Cartenza's response:** organize the log into packages — conceptually like sections of a notebook, but configurable per the work. Humans and agents contribute to the same durable body of knowledge, and a package can define what kinds of information belong in it and how they should be captured, without needing to cram every rule into one giant system prompt.

**What this looks like in practice:** every `knowledge_repo` entry lives in a named package (this handbook's own `log_book`, `knowledge_packages`, `routines` and so on are examples). `browse_knowledge_repo` and `search_artifacts` let you query within a package.

### Config entries: content that describes how to write the other content

Some entries aren't subject matter at all — they record how entries in this repo should be written. Three kinds matter:

| Entry type | What it calibrates | How many |
|---|---|---|
| **`behavior_config`** | Judgment quality — how much rigor, what "good" looks like for this engineer and this repo. No Cartenza default; it is genuinely personal | One per repo |
| **`{type}_configuration`** | Structural shape for a type family — headings, required fields, sections, footer conventions. `note_configuration` covers note/milestone/issue; there are also `decision_configuration`, `observation_configuration`, `lesson_learned_configuration` | One per repo, per family |
| **`purpose`** | What this repo is actually for, and who it serves | One per repo |

**All of them are found repo-wide, regardless of which package they physically live in.** That is what `get_repo_config(config_type=...)` is for: it scans every package's index and returns the match. Don't guess at a package, and don't browse each one hoping to find it — there is no reliable "config lives in the first package" rule, and a real repo was found with its `behavior_config` sitting in the second-listed package.

**A config entry still lives somewhere.** It is an ordinary entry in an ordinary package; only its discovery is special.

### Two disciplines that make this work

**Check before you write.** Early in a session, before logging content, look for the relevant config — `get_repo_config(config_type="behavior_config")` and the matching `{family}_configuration`. If found, apply it. If not, fall back to general judgment or this handbook's default shape. **Both are safe, and a missing config never blocks the work someone asked for.** Check once per repo per session, not before every entry.

**Revise in place; never add a second one.** These are singletons, and the singleton-ness is enforced by discovery rather than by a write-time check. Nothing stops you creating a duplicate — but if you do, `get_repo_config` stops returning an answer and returns **`status: "conflict"`** instead, listing every match and asking a human to resolve it. Every caller relying on that config then has none.

So the convention is: **search first, then revise in place** via `add_log_entry(entry_id=<the one you found>, ...)`. Git keeps the full history, so revising loses nothing.

### Not singletons, but still repo-wide

**`routine_def` entries are many, and discoverable across the whole repo** via `list_routines` — being findable repo-wide and being a singleton are separate properties, and routines have the first without the second.

**A concrete signal you're working at this level:** you've started organizing entries into more than one package with a real reason for the split (not just "everything in one bucket"), and you're searching and browsing past entries rather than only adding new ones — you're starting to *reuse* captured knowledge, not just accumulate it.
