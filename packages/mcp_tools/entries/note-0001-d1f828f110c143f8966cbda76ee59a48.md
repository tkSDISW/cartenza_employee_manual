## Working Through MCP Tools — Where Cartenza's Value Shows Up

**The constraint this solves:** an AI assistant working from memory can only talk *about* your work. It can explain what a functional exchange is, but it can't tell you which of the twenty-eight in your model are missing an exchange item. It can describe good logging practice, but it can't read what you decided last Tuesday. Everything it says is general, and you still have to do the checking.

**Cartenza's response:** give the agent tools that act on the real thing. MCP (Model Context Protocol) servers expose real systems as tools an agent can call: a git repository of your notes, a workspace of routine outputs, a system model. Once connected, the agent stops reasoning from general knowledge and starts working on your actual data. It reads what's there, changes what you ask it to, and reports what it found rather than what's usually true.

This is where the rest of the handbook pays off. A log book is useful to a person; it becomes far more useful once an agent can search it before answering. A routine is a recipe until a tool can run it against real inputs.

**Every Cartenza server is an MCP tool.** `knowledge-repo`, `workspace-manager` and `project-artifact-repo` are covered in `getting_started`. This package covers tools that reach **beyond** Cartenza's own storage into systems you already work in.

### capella-fabric, the first example

**capella-fabric connects an agent directly to a Capella system model** stored in git. It can browse the model's layers, search for elements, pull a structured view of them, and apply changes back: add functions and components, set names and descriptions, allocate exchange items, and verify the result.

It is the clearest demonstration of the idea, for two reasons:

- **It's free.** Capella is open source, and so is the tool, so anyone can see what working through a tool is like without buying anything.
- **The difference is obvious.** Ask a general assistant about your model and it can only guess. Ask one connected through capella-fabric and it answers from the model itself, with element IDs you can check.

### How to think about any tool here

Three habits carry across every tool in this package:

1. **Each server's own `instructions` field is the authority on its mechanics.** It arrives when you connect and stays current with the server. When this handbook and those instructions disagree on syntax, trust the instructions.
2. **Tools that change things deserve a confirm step.** Reading is cheap and safe. Writing to a real model or repo should be stated, confirmed, done, and then verified.
3. **Keep the work and the record separate.** A tool that changes a model is not where you log *why* you changed it; that goes in `knowledge-repo`. Two servers, two sessions.

**A concrete signal you're working at this level:** you've stopped asking an agent to describe your data and started asking it to go and look.
