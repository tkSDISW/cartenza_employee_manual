## What Is a Workspace, and What Can I Put in It?

**The constraint this solves:** a routine execution produces work *before* anyone knows which parts of it are worth keeping. Drafts, intermediate tables, a fabric that turned out wrong, a summary that got superseded. If every one of those landed in a permanent home, the permanent home would stop being meaningful. A workspace is where a routine's outputs live while the work is still in progress.

**A workspace is scratch space for one routine execution — not a permanent home.** It is deliberately separate from `knowledge_repo` (the durable log of what happened and why) and from `project_artifact_repo` (where a finished, promoted output lives long-term). Nothing moves out of a workspace on its own.

### Two modes, chosen when the workspace is created

`create_workspace(session_id, routine_id, engineer=None, mode="folder")`

| Mode | Where outputs live | When to choose it |
|---|---|---|
| **`folder`** (default) | `workspace/{routine_id}/{date}/` on the current branch | Fast, low-risk routines with no concurrent-write risk. Still committed as written, still resumable — there is just no new branch |
| **`branch`** | an isolated branch, `workspace/{routine_id}-{date}` | Long-running or failure-prone routines, where you want to inspect mid-process output while diagnosing a failure and abandon a bad run cleanly without touching history. Also the right choice for team routines, where two people might run the same routine at once and need write isolation |

**The mode is fixed when the workspace is created.** There is no tool to switch an existing workspace between modes — if you need the other one, create a new workspace. The `workspace_id` itself tells you which mode you got: `{routine_id}/{date}` for folder, `workspace/{routine_id}-{date}` for branch.

**One visibility difference worth knowing before it surprises you:** `list_workspaces` shows folder-mode workspaces **only while their branch is the one currently checked out**. Branch-mode workspaces are visible no matter what is checked out. A folder-mode workspace that seems to have vanished has almost certainly not — you are on a different branch than the one it lives on.

### What you can put in a workspace — typed artifacts, not loose files

Every workspace artifact carries a declared type, checked when it is written: `table`, `yaml`, `text`, `html`, `json`, `arcadia_fabric`, `session_summary`, `prompt_def`, `prompt`.

**Writing one:**

```
write_workspace_artifact(session_id, workspace_id, package, type, name, content_str, tags=None)
```

Committed immediately, into the workspace — not onto whatever branch you happen to be on. Note the `package` argument: artifacts are organised into packages inside a workspace just as they are everywhere else in Cartenza.

**Reading one:** `read_workspace_artifact(session_id, workspace_id, output_name)`, where `output_name` is the `name` you passed when writing. This never checks out or disturbs the session's current branch — folder mode reads from disk, branch mode reads via `git show`.

**Checking on the whole workspace:** `get_workspace_status(session_id, workspace_id)` returns its status plus its manifest — the outputs written so far.

### Promotion is always two explicit calls, never automatic

A finished workspace artifact does not become permanent on its own. Moving one into `project_artifact_repo` is two separate steps, deliberately:

```
1.  workspace_manager.read_workspace_artifact(session_id, workspace_id, output_name)
        -> {content_str, type}

2.  project_artifact_repo.write_artifact(session_id, package, type, name, content_str)
        -> places it in its permanent home
```

These are two different servers with two different sessions, and the `session_id` in each call belongs to that server. Mixing them up is the most common way this goes wrong.

`write_artifact` also accepts `source_tool` and `lineage`, which record where a promoted artifact came from. Worth filling in — a promoted output with no trace back to the execution that produced it is harder to trust six months later.

**Then log the promotion** in `knowledge_repo`:

```
add_log_entry(..., entry_type="decision", artifact_refs=[{...}])
```

so the durable record says the promotion happened and why — not merely that the artifact now exists somewhere.

**Why the separation matters, and not just how it works:** most of what a routine drafts is genuinely disposable. Requiring an explicit promotion means only what is actually worth keeping reaches `project_artifact_repo`, instead of every intermediate output accumulating there by default. Promotion is a judgment, so it is a decision someone makes — never a side effect of the routine finishing.

### When the work is done

`close_workspace(session_id, workspace_id)` marks it complete. **It does not delete or rename anything.** A branch-mode workspace's branch is left on the remote indefinitely; a folder-mode workspace's status simply flips in place. Work you did always remains reachable, including work from a run you abandoned.
